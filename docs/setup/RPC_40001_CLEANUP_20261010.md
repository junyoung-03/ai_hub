## Error compatibility details

All six RPCs are server-only service_role calls through supabase-js/PostgREST; no browser calls. Search checks SQLSTATE (not raw HTTP status/message), maps stale to STALE_INPUT/409 and unrelated failures to 503. A stale semantic query cache can run one cleanup release and fall back to keyword results; this is existing behavior, not transaction replay. Index errors may run one best-effort fail operation and then return the error; no immediate retry loop. Existing bounded index cycle/retry policy is unchanged.
Drive persistence checks code only and returns one failed per-file SOURCE_CHANGED result. Calendar checks code only internally and increments batch failed; it does not expose per-event errors. Neither repeats a persistence RPC on conflict. Their Google HTTP 429/5xx retry is separate and unchanged.
Both scope upgrades inspect error presence/data identity, not SQLSTATE/message/HTTP status. PT409 keeps GoogleConnectionStorageUnavailableError, OAuth callback storage_unavailable redirect (the existing connection error helper uses TOKEN_STORAGE_UNAVAILABLE/503). This existing generic contract is intentionally preserved rather than adding a new OAuth response. One RPC call per upgrade, no database retry.
