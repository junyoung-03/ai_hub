# 동시 요청과 처리 지연 이해하기

작성 기준: 2026-10-27 저장소 코드. 이 문서는 현재 구현과 개선 아이디어를 설명하는 학습 자료이며, 새로운 제품 요구사항을 확정하는 문서가 아니다. 운영 환경의 설정과 실제 처리 성능은 별도 확인이 필요하다.

## 1. 두 문제의 차이

**동시 요청에 따른 데이터 충돌**은 여러 작업이 같은 자료를 비슷한 시간에 변경하면서 결과가 꼬일 수 있는 문제다. 예를 들어 휴대폰에서 할 일을 완료하는 동안 PC에서도 같은 할 일을 수정하면, 늦게 끝난 요청이 먼저 반영된 변경을 덮어쓸 수 있다.

**처리 지연**은 처리할 일이 서버, 데이터베이스 또는 외부 AI API가 감당할 수 있는 양보다 많거나 개별 작업이 오래 걸려서 기다리는 시간이 늘어나는 문제다. 오래 기다리다 요청의 제한 시간을 넘으면 시간 초과가 발생할 수 있다. 데이터 충돌이 없어도 지연은 생길 수 있다.

서로 다른 사용자가 파일을 올리면 자료는 사용자 ID를 기준으로 구분되므로 보통 같은 기록을 덮어쓰지 않는다. 하지만 서버·DB·Gemini API는 공유하므로 이용량이 몰리면 서로의 대기 시간에 영향을 줄 수 있다.

## 2. 현재 코드에서 확인할 수 있는 충돌 대응

### 조건부 갱신

서버가 자료를 읽은 뒤 저장할 때, 읽었던 수정 시각(`updated_at`)이나 상태가 여전히 일치하는지 확인하는 방식이다. 다른 요청이 먼저 변경했다면 조건이 맞지 않아 기존 내용을 그대로 덮어쓰지 않는다. 이후 다시 읽고 처리하거나 충돌을 알린다.

예를 들어 Action 상태 변경은 소유자와 현재 상태·수정 시각을 확인해 조건부로 변경한다. 이미 요청한 상태라면 다시 쓰지 않고, 변경이 겹치면 제한된 횟수 안에서 다시 확인한다. 이는 다른 요청의 변경을 발견하는 장치이지 동시 요청이 발생하지 않게 만드는 장치는 아니다.

### 잠금과 트랜잭션

DB 잠금은 같은 데이터 등을 동시에 변경하는 작업의 순서를 조정한다. 관련 데이터를 저장하는 DB 함수는 트랜잭션으로 처리하므로 중간에 실패하면 해당 트랜잭션의 DB 변경을 되돌린다. 예를 들어 Action과 근거를 연결하는 중 오류가 나면 일부만 확정되는 상황을 줄인다.

RPC는 서버가 DB 함수를 호출하는 방법이다. RPC 자체와 트랜잭션은 다른 개념이다. 또 DB 트랜잭션은 외부 Gemini 호출이나 이미 Storage에 저장된 원본 파일까지 되돌리지 않는다.

### 제한된 DB 저장 재시도

분석 결과 저장 코드에서는 교착 상태(`40P01`) 또는 직렬화 실패(`40001`)가 발생하면 저장 RPC 전체를 최초 시도 포함 최대 3회 시도한다. 이미 받은 AI 분석 결과로 저장을 다시 시도하며, 이 때문에 Gemini를 다시 호출하는 것은 아니다. 모든 오류를 재시도하는 것은 아니다.

교착 상태는 두 작업이 서로 상대방의 잠금 해제를 기다리는 상황이다. 직렬화 실패는 DB가 동시에 진행된 작업을 안전하게 확정할 수 없다고 판단해 한 작업을 중단하는 경우다. 모두 해결된다는 보장은 없으며 시도 후에도 실패하면 오류를 반환한다.

### 작업 토큰과 유효기간

일부 백그라운드 작업은 작업을 처리할 권한을 나타내는 토큰과 유효기간(lease)을 사용한다. 유효한 작업인지 확인해 오래된 작업이 늦게 결과를 저장하거나 다른 작업과 중복 처리하는 것을 막는 데 활용한다. 이 방식이 서비스의 모든 처리 경로에 적용된 것은 아니다.

## 3. 현재 코드에서 확인할 수 있는 지연 관련 장치

- **입력 크기 제한:** 처리할 수 있는 파일·본문 등의 크기를 제한해 무거운 요청을 일정 범위로 관리한다. 분석 코드에는 본문 길이 제한도 있다.
- **정상 결과 재사용:** 본문과 모델·분석 스키마 등의 fingerprint를 비교해 조건이 맞는 기존 결과를 재사용한다. 매 요청마다 같은 분석을 반복하는 부담을 줄인다.
- **일부 Gmail 작업 큐:** 설정이 활성화되고 허용된 사용자의 Gmail 분석에 한해 요청을 큐에 넣는 경로가 있다. 실제 운영에서 켜져 있는지는 환경변수와 실행 환경을 확인해야 한다.
- **작업별 재시도와 복구 장치:** 일부 백그라운드 경로에 제한된 재시도와 lease가 있다. 모든 업로드와 분석이 항상 큐로 처리되거나, 모든 오류에 같은 재시도 정책이 적용되는 것은 아니다.

현재 코드의 장치가 모든 상황에서 지연이나 시간 초과를 막는다는 뜻은 아니다. 대규모 사용자를 대상으로 처리량과 대기 시간을 검증한 결과도 이 문서에서 확인하지 않았다.

## 4. 요청이 몰리면 어떻게 대응할 수 있나

다음은 개선 방향이며, 전부 현재 구현됐다는 뜻은 아니다. 먼저 어느 구간이 느린지 측정하고 우선순위를 정해야 한다.

1. **긴 작업을 큐에 넣기:** 요청을 접수하고 작업 상태를 기록한 뒤 작업 처리기(Worker)가 가능한 만큼 처리한다. 사용자에게 대기·처리 중·완료·실패를 보여준다. 큐 자체가 분석 속도를 높이지는 않지만, 짧은 웹 요청과 긴 작업을 분리하고 몰린 요청을 관리하는 데 도움이 된다.
2. **동시 실행 수와 요청량 제어:** Worker가 동시에 처리하는 개수와 사용자별 요청량을 제한한다. Gemini의 요청 및 토큰 한도에 맞춰 속도를 조정하고, 특정 사용자 때문에 다른 사용자가 계속 기다리지 않도록 공정성을 고려한다.
3. **중복 작업 줄이기:** 동일한 자료와 분석 조건에서 이미 완료된 결과를 안전하게 재사용한다. 내용이나 모델·스키마가 바뀌면 재사용 가능 여부를 다시 판단한다.
4. **일시 오류에 간격을 둔 재시도:** 일시적인 네트워크 오류나 API 과부하에는 제한된 횟수로 기다림을 늘려 재시도하는 방식을 검토한다. `Retry-After` 안내가 있으면 해당 서비스의 정책을 따른다. 인증 오류나 잘못된 입력을 무한 재시도하지 않는다. 일일 사용량 한도를 소진한 경우 짧은 간격의 재시도로 해결되지 않을 수 있다.
5. **중단 복구와 중복 방지:** 작업이 중단되면 유효기간 이후 다시 처리할 수 있게 하고, 같은 작업이 재실행돼도 결과가 중복 저장되지 않도록 설계한다. 오래된 작업의 결과가 최신 데이터를 덮어쓰지 않도록 확인한다.
6. **병목 확인 후 용량 조정:** 업로드, 텍스트 추출, Gemini 호출, DB 저장, 검색 색인에 걸린 시간과 실패 원인을 각각 측정한다. DB가 느리면 조회와 인덱스를 점검하고, 추출이 병목이면 작업 크기나 처리기 용량을 검토한다. 웹 서버를 늘려도 외부 API의 한도가 자동으로 늘지는 않는다.

## 5. 검증할 항목

- 같은 사용자의 같은 Action을 동시에 변경할 때 결과가 일관되고 충돌을 적절히 알리는가?
- 다른 사용자의 자료가 섞이거나 서로 보이지 않아야 할 자료에 접근되는가?
- 같은 자료의 중복 분석에서 불필요한 API 호출이나 중복 Action이 발생하는가?
- 큐 사용 경로에서 작업 중단·토큰 만료·재시도 후 중복 저장 없이 복구되는가?
- 요청량을 단계적으로 늘렸을 때 각 단계의 처리 시간, 대기 시간, 실패율과 시간 초과는 어떻게 변하는가?
- 외부 API의 일시 오류와 사용량 한도 도달 시 사용자에게 현재 상태가 올바르게 표시되는가?

검증은 테스트용 계정과 데이터로 수행하고, 실제 운영 환경의 활성 설정도 별도로 확인한다.

## 6. 발표할 때 이렇게 설명하기

> 여러 요청이 같은 데이터를 변경할 때는 수정 시각과 상태를 비교하고, 관련 DB 저장은 트랜잭션으로 처리합니다. 일부 일시적인 DB 충돌은 저장 작업 전체를 제한적으로 재시도합니다.

> 서로 다른 사용자의 자료는 구분되지만 서버와 AI API 자원은 공유하기 때문에 요청이 몰리면 지연이 생길 수 있습니다. 현재 일부 경로에 결과 재사용과 작업 큐가 있고, 장기적으로는 대기열·동시 처리량 관리와 부하 검증이 필요합니다.
